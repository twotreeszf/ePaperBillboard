# 电子书阅读器项目规划

参考项目：[Papyrix](https://github.com/bigbag/papyrix-reader)（MIT 协议，评估基于 commit `ee071b17`，2026-10-07）。

当前进度见第 11 节：TXT 阅读第一期（M0 的 cmap 加速、M1、M2 的 SD 卡服务部分）已编码并编译通过，待真机验证。

## 1. 结论

Papyrix 适合当作设计和代码来源，不适合整体移植。它的前提和本设备差别很大：

| 项目 | Papyrix | 本设备 |
|---|---|---|
| 书和缓存存储 | SD 卡，容量充足 | 板上有 SD 卡槽，驱动尚未开发；内置 LittleFS 在 8MB 板上约 1MB 空闲 |
| 内存 | ESP32-C3 约 400KB，部分型号带 PSRAM | ESP32-WROOM-32E 约 320KB，无 PSRAM |
| 字体 | 内置 2bpp 字体，拉丁斜体为单独字体 | 1bpp 思源黑体 10/12/16px，流式读取 |
| 输入 | 多按键 + 触摸 | 左、右、中 3 个按键，支持单击和长按 |

因此核心架构重新设计为三层：

1. **导入层**：各种格式在导入时转换为统一的中间文本流（flow 文件）。TXT 例外，直接读取。
2. **分页索引层**：只记录每页起点，体积很小，后台分批建立，可中断续建。
3. **渲染层**：翻页时从页起点现场排一页，用一个自绘 LVGL 对象画出来。

斜体和粗体由现有字体在取字形回调里实时生成，不新增字体文件。EPUB 里的图在导入时转成整页线稿；解不出来的图仍用「〔图〕」。

## 2. 从 Papyrix 借鉴的内容

### 2.1 借鉴或直接改用

- **`ContentParser` 接口**（`lib/PageCache/src/ContentParser.h`）：`parsePages(onPageComplete, maxPages, shouldAbort)` 一次只解析 N 页，`canResume()` 支持接着上次继续。这是低内存流式解析的核心模式。
- **Markdown 解析器**（`lib/Markdown/src/md_parser.c`，462 行）：按行扫描，用回调输出标记，不建语法树，状态只有几十字节。md4c 需要把整篇文档放进内存，不支持流式，不采用。
- **段落内存上限**（`MarkdownParser.cpp`）：段落超过 300 词时，若达到 `kMaxWordsPerBlock` 或最大连续空闲内存低于 25KB，就在行边界提前排版输出，避免超长段落耗尽内存（Papyrix Issue #137）。
- **TXT 分页索引**（`docs/file-formats.md` 中的 `index.bin`）：只存每页在源文件中的字节起点；文件大小、版心宽度或每页行数变化时整体重建。
- **总页数估算**（`PageCache::estimatedTotalPages`）：索引未完成时按"已解析字节 / 总字节"推算总页数。
- **功能设计**：最近阅读、书签、阅读统计、目录、每 N 页全刷、排版预设。

### 2.2 不采用

- **整页序列化缓存 `PageCache`**：每页保存每个词及其坐标，写入量大、建缓存慢。即使有 SD 卡，只存页起点的索引也足够，翻页时现场排一页的开销很小。
- **expat**：Arduino-ESP32 3.3.12 框架未自带，引入后固件至少增加约 100KB。当前固件 1.59MB，分区上限 2MB。
- **Knuth-Plass 两端对齐**：内存峰值高。Papyrix 自己也默认使用贪心换行。
- **其他**：阿拉伯文和泰文排版、前光、触摸分区、IPP 打印、LocalSend、XTC 格式、按设备区分的缓存目录。

## 3. 低内存流式解析

### 3.1 flow 中间格式

EPUB、Markdown、HTML、FB2 在导入时解析一次，生成 `/books/<id>/book.flow`：

- **文件头**：魔数 `TTFL`、版本、源文件大小、源文件指纹、书名、作者、章节数。
- **正文**：UTF-8 文本，夹带以下控制字节（取自正文中不会出现的 C0 控制字符）：
  - `0x01 <flags>`：样式状态，按位表示粗体、斜体、代码。
  - `0x02 <type>`：块开始，类型包括段落、标题 1 到 3 级、引用、列表项、代码行、分隔线、居中。
  - `0x03 <index>`：章节标记。
  - `\n`：块结束。
- **目录**：单独写到 `toc.bin`，每条记录 flow 偏移、层级、标题。

这样设计有两个原因：一是阅读器只处理一种输入；二是 EPUB 正文是 deflate 压缩流，不能从中间解压，先转成 flow 后，翻页只需普通的文件定位和读取。

TXT 不转换，直接作为 flow 源读取（没有控制字节）。几 MB 的小说再转一遍既费时间又重复占用存储。章节在建索引时顺便识别，规则为匹配行首的"第X章 / 第X回 / 第X节 / 卷X / Chapter N"，并限制标题行长度。

### 3.2 分页索引

每种排版配置一个 `/books/<id>/pages_<配置哈希>.bin`：

- **文件头**：配置哈希（字号、行距、缩进、段距、对齐、版心尺寸）、源大小、已建页数、是否完成、已解析字节。
- **每页 8 字节**：
  - `uint32` flow 中的起点偏移；
  - `uint8` 当时的样式状态；
  - `uint8` 当前块类型；
  - `uint8` 标志位，例如是否处在段落中间、是否要首行缩进；
  - `uint8` 保留。

体积估算：100 万字的书在 16px 下约 3500 页，索引约 28KB。

建立方式：

- 打开书时，从保存的进度位置现场排出第一页，立即显示。
- 后台用 LVGL 定时器分批建立，每批约 5 页、耗时不超过约 50ms，每批完成就落盘。
- 设备休眠后，醒来从已建的位置继续。
- 排版配置变化时，按页起点偏移换算回新索引中最近的一页，保持阅读位置。

### 3.3 内存预算

阅读时的增量：

| 项目 | 大小 |
|---|---|
| 读文件缓冲 | 4KB |
| 当前页文本缓冲（16px 一页约 360 个汉字） | 约 2KB |
| 行和样式段表 | 约 1KB |
| cmap 子表头常驻内存（`all_16.bin` 共 204 张子表） | 约 3.3KB |
| 字形信息缓存（由 64 项扩到 256 项） | 约 4KB |
| 字形点阵 LRU 缓存（可选，按 M0 实测决定） | 约 16KB |

合计约 15 到 30KB，可与现有的 15KB 整屏缓冲和 32KB LVGL 内存池共存。

EPUB 导入时的峰值：

| 项目 | 大小 |
|---|---|
| 解压回溯窗口 | 32KB |
| `tinfl` 解压器状态 | 约 11KB |
| 压缩数据输入缓冲 | 4KB |
| XHTML 解析器状态 | 约 2KB |

合计约 50KB。ESP32 ROM 内置 miniz 的 `tinfl` 解压函数（`esp_rom/include/miniz.h`），不占固件空间。导入在 WiFi 关闭后进行，开始前检查最大连续空闲内存，不足时提示并放弃。

### 3.4 各格式解析

- **TXT**
  - 每次读 4KB，跳过 BOM，统一行尾，按换行或空行分段。
  - 中文 GBK/GB18030 文件：推荐在上传页面里用浏览器的 `TextDecoder('gb18030')` 转成 UTF-8 后再上传，固件零成本。备选方案是设备端内置约 44KB 的 GBK 转 Unicode 表。
- **Markdown**
  - 移植 Papyrix 的 `md_parser`，保留 MIT 版权声明。
  - 代码块围栏、列表等跨行状态由外层维护，输出写入 flow。
- **EPUB**
  1. 从文件尾部定位 ZIP 中央目录，逐条流式读取，不一次性加载。
  2. 解析 `META-INF/container.xml`，找到 OPF。
  3. 解析 OPF 的 manifest 和 spine，得到阅读顺序。
  4. 解析 NCX（EPUB 2）或 nav（EPUB 3），得到目录。
  5. 每个章节用 `tinfl` 流式解压，送入自写的宽松 XHTML 解析器（约 300 行），写入 flow。
  - 解析器只处理 `p`、`div`、`h1`-`h6`、`em`、`i`、`strong`、`b`、`li`、`blockquote`、`br`、`hr`、`a`，属性只取 `id`、`href`，并解码常用 HTML 实体。
  - 图片输出"〔图〕"占位。
- **FB2 / HTML**：复用同一个 XHTML 解析器，放到后期。

## 4. 字体方案与 LVGL 结合

### 4.1 cmap 查找加速（必须先做）

`TTFontLoader::_getGlyphID` 目前逐个遍历 cmap 子表，每张子表都要从文件定位并读取 16 字节。`all_16.bin` 有 204 张子表，一个未缓存的字最坏要做约 200 次文件读取；一页中文三百多个不同的字，这里会成为翻页的主要耗时。

改法：

- `begin()` 时把子表头读入内存，按起始码位排序后二分查找。
- 稀疏子表（类型 1 和 3）的码位差值列表也改为二分查找。目前最大项数：16px 为 21 项，12px 为 137 项。

这项优化对现有界面同样有效。

### 4.2 页面渲染：自绘对象

新增阅读视图控件 `TTReaderTextView`：

- 一个 `lv_obj`，在 `LV_EVENT_DRAW_MAIN` 中按"行 → 样式段"逐段调用 `lv_draw_label`，每段使用对应样式的字体。
- 文本放在页面自己的缓冲中，不占 LVGL 的 32KB 内存池。
- 现有驱动使用 15KB 整屏缓冲加 `LV_DISPLAY_RENDER_MODE_PARTIAL`，一帧只绘制一次，每个字形只取一次。
- 不开启 `LV_USE_SPAN`。换行、禁则、对齐由自有排版引擎完成，LVGL 只负责绘制。
- 排版时量字宽和绘制使用同一个取字形回调，保证宽度一致。

### 4.3 样式变体

- `TTFontManager` 新增按"字号 + 样式"取 `lv_font_t*` 的接口。
- 同一字号的常规、粗、斜、粗斜四个 `lv_font_t` 共用同一个 `TTFontLoader`，即同一组文件句柄和缓存。
- 样式标志放在 `lv_font_t.user_data`。回调中通过 `dsc->resolved_font->user_data` 取得样式并做变换。
- 现有界面的 label 也可以直接使用斜体和粗体。

### 4.4 字号规划

- 正文：12px、16px。16px 在 400×(300 − 导航栏) 的版心中约每行 23 字、14 行。
- 页眉页脚：10px。
- 量产 16MB 后可考虑新增 20px，或换用更适合阅读的思源宋体，单个字号约 2.3MB。
- `TTFontLoader` 已支持"主字体 + 优先使用的 ASCII 字体"（`asciiPath`）。以后为英文配衬线字体，不需要改动结构。

## 5. 由现有字体生成斜体和粗体

### 5.1 斜体：以基线为轴水平错切

- 斜率用宏定义，例如 `TT_FONT_ITALIC_SLANT_X1000 200`（约 11°），CJK 可单独用 `150`。
- 字形第 y 行（自上而下，从 0 开始）相对基线的高度为 `h = ofs_y + box_h - 1 - y`，该行右移 `s(h) = round(h * k)`。
- `lvglGetGlyphDsc`：
  - `box_w += s(顶行) - s(底行)`；
  - `ofs_x += s(底行)`，降部向左偏，可能为负；
  - `adv_w` 不变，排版宽度与正体一致。
- `lvglGetGlyphBitmap`：逐行解码原 1bpp 点阵，按 `s(h)` 偏移写入 LVGL 绘制缓冲。现有的缓冲尺寸和 stride 检查在盒子变宽后照样适用。
- **斜体修正**：斜体段后紧接正体时，排版引擎补 `s(顶行)` 像素间距，避免斜体顶部压到后面的字。
- 成本：每个字形多一次行偏移循环，CPU 开销可忽略，内存为零。1bpp 下每约 5 行出现一个像素台阶，在墨水屏上表现为自然的锯齿。

### 5.2 粗体：右移 1 像素叠加

- 点阵右移 1 像素后与原图按位或。
- `box_w += 1`，`adv_w += 1`。
- 小字号中文笔画容易粘连，正文粗体建议只用于标题，或只在 16px 及以上启用。

### 5.3 中文强调方式

中文正式排版通常不用斜体，而用楷体或着重号表示强调。设置项"强调方式"提供"斜体 / 着重号"两个选项。着重号在自绘视图中于字下方画点，零成本。

## 6. 排版引擎

- **中文**：按字断行。
  - 禁止出现在行首：`，。、；：？！）」』》〉】〕…—` 等。
  - 禁止出现在行尾：`（「『《〈【〔` 等。
  - 处理方式：前一行挤压或把一个字推到下一行。
- **英文**：按词贪心换行，超长单词按字符强制断开。断字放到后期。
- **对齐**：两端对齐时，中文把多余空间均分到字间，英文分到词间；段末行左对齐。标题居中。
- **段落**：首行缩进 0、1、2 个字宽，段距 0、0.5、1 行，三档预设。
- **行距**：紧凑、标准、宽松三档。

## 8. 存储

板子带 SD 卡槽，书、flow 文件、索引和进度都放在 SD 卡上，因此存储空间不作为约束。SD 卡驱动尚未开发，接入前开发调试可以先用内置 LittleFS（8MB 板上约 1MB 空闲，可放一两本书）。字体继续放在内置 LittleFS。

存储访问通过一层统一的文件接口，SD 卡和 LittleFS 可以切换，阅读器代码不感知具体介质。

### 8.1 硬件连接

| 信号 | ESP32 引脚 | 卡座引脚 | 说明 |
|---|---|---|---|
| SD_SCLK | IO13 | CLK | |
| SD_MOSI | IO12 | CMD | 启动引脚，开机为高电平时 Flash 电压会被设成 1.8V |
| SD_MISO | IO15 | DAT0 | 启动引脚，影响启动日志输出 |
| SD_CS | IO14 | CD/DAT3 | SPI 模式下作片选 |
| CARDDETECT | IO2 | CD（卡座检测开关） | 启动引脚；插卡时开关接 GND，读到低电平表示有卡 |
| SDVDD_CTRL | IO27 | 经 SI2301 控制卡电源 | 低电平上电；栅极 100kΩ 上拉，开机和深睡时默认断电 |

- 墨水屏使用 IO16、IO4、IO17、IO5、IO18、IO19，与 SD 卡不重叠。墨水屏用全局 `SPI`（VSPI），SD 卡用独立的 `SPIClass(HSPI)`，**不需要总线互斥**。
- 这组引脚不符合 ESP32 SDMMC 控制器的固定引脚（CLK=IO14、CMD=IO15、D0=IO2），**只能用 SPI 模式**，使用 Arduino 自带的 `SD` 库。信号经 GPIO 矩阵路由，SPI 时钟 20MHz 左右可用，读取约 1 到 2MB/s。
- 卡在开机时不上电，不会把 IO12、IO15、IO2 拉到错误电平，不影响启动和下载固件。
- 原理图上 SD 信号线没有外部上拉，DAT1、DAT2 悬空。

### 8.2 驱动方案

参考硬件原作者的 LiClock 工程（`.ref/LiClock/src/peripherals.cpp`、`hal.cpp`），引脚定义与原理图一致，以下做法已在该工程中验证：

- 开机：IO2 设为 `INPUT_PULLUP`，IO27 输出高电平（卡断电）。
- 总线：`SPIClass(HSPI).begin(SCLK, MISO, MOSI, -1)`，片选交给 `SD.begin(PIN_SD_CS, spi)` 管理。
- 挂载：检测 IO2 为低电平 → IO27 拉低 → 等待 50ms → `SD.begin`；失败则等 100ms 重试一次，仍失败提示"存在 TF 卡，但无法挂载"。
- 卸载：`SD.end()` → 等待 50ms → IO27 拉高。
- 按需使用：每个应用声明是否需要 SD 卡，切换应用时统一挂载或卸载。
- 深睡：进入深睡前卸载，唤醒后按原需求重新挂载。

在此基础上的改进：

1. **断电前释放信号线**：`SD.end()` 后先把 IO12、IO13、IO14 设为输入，再拉高 IO27，避免信号线经卡内保护二极管倒灌供电。
2. **MISO 上拉**：IO15 开启内部上拉。
3. **提高时钟**：LiClock 用默认的 4MHz，我们先试 20MHz，实测不稳定再降频。
4. **插拔检测**：书库页定时检测 IO2，拔卡后立即卸载并提示。
5. **上电冲击电流**：SD_VDD 上有 10µF 电容（C19），Q5 导通瞬间会把 3V3 拉低并触发欠压复位。2026-10-19 实测：C19 对地没有短路；同一张 32GB 卡在一台板上偶发、在另外两台上必现。短脉冲预充电只在余量较大、且卡上次是正常断电时有效，上电一旦被复位打断，下一次冲击会更大，预充电也会失败。LiClock 也是直接拉低电源脚，没有做缓冲。当前在 `setup()` 开头调用 `Util::disableBrownoutDetector()` 关掉欠压复位，卡可以完成上电。电压跌落本身还在：如果跌落发生在读 Flash 期间，不会再有一次干净复位，可能跑飞或损坏文件系统。硬件上更稳妥的做法是加大 3.3V 储能（现在主要靠 C7 的 10µF），或在 Q5 栅极加 RC，把导通沿拉慢。
6. **服务化**：做成独立的 SD 卡服务，负责挂载、卸载和上下电。页面通过引用计数申请和释放，深睡流程接入卸载；空闲约 30 秒自动卸载并断电。重新上电挂载约 0.2 到 0.3 秒。
7. **框架差异**：LiClock 使用 Arduino-ESP32 2.x，我们是 3.3.12；`SD.begin(cs, spi, freq)` 接口一致。
8. **并发**：ESP-IDF 的 FatFs 自带锁，UI 任务读书和 WiFi 任务上传可以同时进行。

LiClock 的电子书（`src/apps/appEBook.cpp`）只支持 UTF-8 TXT：首次打开时在书旁生成 `<书名>.i` 分页索引（每页 4 字节偏移），当前页存 `RTC_DATA_ATTR` 并在退出时写入偏好设置。思路与本规划一致，可作为 M1 的参考。

### 8.3 TF 卡要求

- **文件系统只支持 FAT32**：框架的 FatFs 配置为 `FF_FS_EXFAT 0`。2GB 到 32GB 的卡出厂即为 FAT32，可直接使用；64GB 及以上出厂为 exFAT，需要强制格式化为 FAT32。
- **中文文件名可用**：长文件名已开启，接口编码为 UTF-8（`CONFIG_FATFS_API_ENCODING_UTF_8=y`）。
- **SPI 模式兼容性**：杂牌卡和扩容卡在 SPI 模式下可能初始化失败。推荐闪迪 Ultra、金士顿 Canvas Select Plus、三星 EVO Plus 的 16GB 或 32GB 款；2GB 到 8GB 的老卡 SPI 兼容性通常最好。
- **速度等级无关紧要**：SPI 模式实际只有 1 到 2MB/s。
- **验货**：二手卡先用 H2testw 或 F3 完整读写一遍，排除扩容卡。

### 8.4 下一版硬件建议

- CMD、DAT0、DAT3 及未使用的 DAT1、DAT2 各加 10k 到 47kΩ 上拉，**接 SD_VDD 而不是 3V3**：既符合 SD 规范，卡断电时也不会把 IO12 拉高或倒灌供电。
- MOSFET 栅极加 RC，使 SD_VDD 缓慢上升，从硬件上消除上电冲击电流。
- 量产前可考虑烧 eFuse 把 Flash 电压固定为 3.3V（`espefuse.py set_flash_voltage 3.3V`，不可逆），彻底消除 IO12 的启动风险。

## 10. 风险

| 风险 | 应对 |
|---|---|
| 固件空间：当前 1.59MB / 2MB，全部功能预计增加 80 到 150KB | 不引入 expat，解压用 ROM 内置的 `tinfl`，XHTML 解析器自写精简版 |
| SD 卡驱动尚未开发，SD 库会增加固件体积 | 方案已有 LiClock 验证；接入前用 LittleFS 开发调试，文件接口统一，后续切换不影响阅读器代码 |
| SD 卡上电冲击电流可能导致欠压复位 | 启动时关闭欠压检测（见 8.2）。短脉冲预充电不能覆盖所有板子和卡的状态。下一版硬件加大 C7 或给 Q5 栅极加 RC |
| IO12、IO15、IO2 是启动引脚 | 卡默认断电，信号线不加接 3V3 的上拉；量产前可烧 eFuse 固定 Flash 电压 |
| 杂牌卡 SPI 模式兼容性差，exFAT 不支持 | 推荐品牌 32GB 及以下 FAT32 卡；挂载失败时明确提示 |
| EPUB 导入时的内存峰值 | 改为在上传网页里转换成 Markdown，设备端不解压（见 11.5） |
| 字库覆盖：生成时排除了 CJK 扩展 A 区和兼容汉字区 | 缺字显示占位符，并在日志中记录缺失码位 |
| 中文斜体观感 | 提供"着重号"强调方式作为替代 |
| 大书建索引耗时数十秒 | 先估算总页数，分批建立，可中断续建 |
| 字体读取不是线程安全的 | 建索引放在 UI 任务的 LVGL 定时器中执行，不另开任务 |

  - 上传网页（内嵌在固件中）：
    - 多选文件后逐个上传，也可以把文件拖到页面任意位置直接上传，拖入时整页显示虚线框。每个文件有进度条；不是 `.txt`、`.md` 或 `.epub` 的文件、超过剩余空间的文件会被跳过。`.epub` 先在浏览器里转成 Markdown（`tools/epub_to_md.js`，内嵌进固件），再以原文件名换成 `.md` 上传，并按转换后的大小检查剩余空间。
    - 列出书架上的书，可以删除（连同阅读进度、分页索引和最近阅读记录）；显示 SD 卡剩余空间和总容量。
  - `TTSdCardService` 的挂载、卸载和查询剩余空间加了互斥锁，因为界面和 Wi-Fi 两个任务都会调用；新增 `spaceInfo()`。
  - `TTBookStore` 新增 `removeBook()`。
- **阅读页浅睡眠**（`TTReaderPage`，未上真机验证）
  - 最后一次按键 5 秒后（`TT_SLEEP_INPUT_IDLE_MS`）先保存进度，再请求浅睡眠；正在建索引时不睡，5 秒后再试，所以大书要等索引建完才会开始睡。
  - 被按键唤醒：这次按键照常翻页，之后重新开始计 5 秒。
  - 每分钟定时唤醒：等导航栏时间更新后马上再睡；如果没有收到时间更新，5 秒后也会再睡。
  - 到了定时同步天气等数据的时间：不留在阅读页等待，直接再请求睡眠，由睡眠服务在射频空闲后进入。
  - 离开页面、弹出退出提示时取消睡眠请求。
  - SD 卡在睡眠期间保持上电和挂载，打开的文件不关闭。
- **内存**（上传失败的原因是接收时空闲内存只剩约 2KB）
  - 进入书架时打开开关，让 Wi-Fi 每次停用时把驱动也卸载（`TTWiFiTask::requestReleaseDriverWhenIdle`，内部调用 `WiFi.mode(WIFI_OFF)`），离开书架时关闭开关。日志：`WiFi: driver released heap=前->后`。
  - `setup()` 结束时删除闲置的 Arduino 主循环任务，释放它的 8KB 栈。
  - LVGL 改为分段渲染：绘制缓冲由整屏 15,008 字节降到 48 行 2,408 字节，堆上多出约 12.6KB（见下一条）。
  - SD 卡同时打开的文件数为 3（`TT_SD_MAX_FILES`：正文、索引、进度）。
- **LVGL 分段渲染**（`TTLvglEpdDriver`、`EPDConfig.h`，已上真机验证）
  - `EPD_BUF_SIZE` 按 `EPD_DRAW_BUF_ROWS`（48 行）计算，外加 8 字节 I1 调色板头（`EPD_I1_PALETTE_SIZE`）。
  - LVGL 每画完一段，只把像素复制进 GxEPD2 自己的整屏缓冲并累计脏区域；最后一段画完后，按脏区域的并集做一次局部刷新，或一次深刷新。屏幕刷新次数与原来相同。
  - GxEPD2 缓冲初始全为 0（黑），所以启动时先填白。`displayWindow()` 不会自动对齐到 8 像素，屏幕旋转为奇数时手动把 y 对齐到 8 的倍数。
  - 代价：整屏要分约 6 段画，跨段的那一行正文会画两次。实测翻页时绘制约 560ms、刷新约 740ms。
- **开机只整屏刷新一次**（`TTUITask`，未上真机验证）：`GxEPD2::init()` 的 `initial` 参数改为 `false`，不再先清屏。原来开机会连续两次整屏刷新，共约 7 秒；第一次 LVGL 刷新本来就是深刷新，会同时写入控制器的两块显存。
- **默认配置**：首次启动时，如果还没有保存任何 Wi-Fi，写入一次默认 Wi-Fi（`TT_WIFI_DEFAULT_SSID`），之后不再写入；没有保存时区时默认用 `CST-8`（`TT_TZ_DEFAULT`）。

### 11.2 与原计划的差异

- **渲染**：不调用 `lv_draw_label`，而是直接写像素。原因是排版器已算好每个字的坐标，直接写可以省掉 LVGL 的逐字测量。
- **存储布局**：用户直接把 `.txt` 放到 `/books/` 根目录；缓存放在 `/books/.cache/<id>/`，内含 `pages_<hash>.bin` 和 `progress.bin`；最近阅读存于 `/books/.cache/recent.txt`。以 `.` 开头的文件（例如 macOS 的 `._`）会被跳过。
- **按键**：
  - 阅读页：左键单击上一页，右键单击下一页，左键长按返回。快速向下拨两下往前翻 10 页，快速向上拨两下往后翻 10 页。单击会先等最多 350ms，用来判断有没有第二下；其他页面的单击不需要等。左键长按是全局返回，所以没有做"长按切章"。中键暂不使用。
  - 书架页：沿用画报选择器的约定，左键向下选、右键向上选，中键打开。
- **`TTPopupLayer`** 新增 `isDialogShown()`。只有弹出对话框时才把左右键交给对话框；提示条显示期间仍然可以翻页。
- **SD 卡服务暂未做**：空闲 30 秒自动卸载、深睡前卸载。阅读页浅睡眠时卡保持上电，不卸载。
- **欠压复位**：SD 卡上电冲击会拉低 3V3。短脉冲预充电已试过，不能在所有板子上稳住，固件改为在启动时关闭欠压检测，详见 8.2 第 5 条。
- **SD 卡不可拆卸**：卡作为内置存储使用，传书只走 Wi-Fi，不提供"拷到 SD 卡"的方式。拔卡检测仍然保留，用于读取出错时安全退出。
- **渲染缓冲**：3.3 节假设的 15KB 整屏 LVGL 绘制缓冲已改为 48 行分段缓冲（约 2.4KB），GxEPD2 自己的 15KB 整屏缓冲不变。
- **EPUB**：不在设备上解压。上传网页用内嵌的 `tools/epub_to_md.js` 转成 Markdown 后再上传，见 11.5。
- **传书方式**：7.2 计划复用配网热点（AP 模式），实际改为 Station 模式：设备连已保存的 Wi-Fi，手机或电脑在同一个网络里访问设备 IP。不用断开原来的网络，速度也更快。没有保存 Wi-Fi 时提示先去 Web 设置。
- **传书页拔卡**：不在界面任务里强制卸载，以免 Wi-Fi 任务正在写文件时被卸载；只停止传书并提示，回到书架后由书架页检测到无卡并退出，最后一份引用释放时卸载。
- **阅读页刷新**：原计划每翻 N 页全刷一次。阅读页改为始终局部刷新，并暂停全局的自动深刷新；离开阅读页后恢复。

### 11.5 Markdown 与 EPUB 方案（按实测内存调整）

**内存余量**
- 改动前打开书时日志为 `free=48380 largest=30708`；分段渲染省下约 12.6KB 后，估计空闲约 60KB，最大连续块仍约 30KB（受 SD 卡挂载时的一次大块分配限制）。需要用真机日志确认。
- 3.3 节的 EPUB 设备端解压需要 32KB 回溯窗口 + 约 11KB 解压器状态，单块就超过最大连续块，而且解压期间还要读写 SD 卡，余量不够。

**Markdown：在设备上解析**
- 已实现，见 11.1。没有移植 `md_parser`，改为自写的逐行解析（`TTReaderMarkdown`），状态只有几个字节。
- 粗体、斜体没有等字体变体，用同一套 16px 字形加粗重画和斜切绘制。

**EPUB：在上传网页里转换**（已编码，待真机验证）
- 转换脚本是 `tools/epub_to_md.js`。本机用 Node 和一份混合存储/deflate 的 EPUB 测过之后，再原样嵌进 `TTBookTransferServer` 的网页。浏览器不额外加载第三方库。
- 用浏览器自带的 `DecompressionStream('deflate-raw')` 解压 ZIP 中的条目。ZIP64 直接提示不支持。
- 读 `container.xml`、OPF 的阅读顺序和目录（优先 EPUB 3 的 nav，否则 NCX），用 `DOMParser` 解析 XHTML，转成 Markdown（标题、段落、强调、列表、任务、引用、代码块、表格）。章节里的 GBK/GB18030 会转成 UTF-8。
- 没有 `h1`–`h6` 时读样式表。短段落（80 字以内）整段字号大于正文时收成标题：1.7 倍及以上为一级，1.4 为二级，1.2 为三级，刚大于正文为四级。`font-weight: bold` 收成粗体，斜体、下划线、删除线同样按样式收。Calibre 从 MOBI 转出的章节名就是这种字号，不是标题标签。
- 图片在浏览器里做 Sobel 边缘，按 aspect fit 画进 400×282 的 TTI1 线稿，和状态栏以上的整页逐像素对应。正文里写成单独一行 `![](0001.i1)`，阅读时这一行独占一页。先上传 Markdown，再把图传到该书缓存目录。图缺失时该页显示「〔图〕」。超过 1600px 的长边会先缩小再取边缘。
- 转换后的文件用原 EPUB 的文件名，只把扩展名换成 `.md`。正文里的书名标题仍取自 OPF。设备端扩展名检查仍然只接受 `.txt` 和 `.md`，固件不增加解压代码。
- GBK 编码的 TXT 仍计划在网页里用 `TextDecoder('gb18030')` 转成 UTF-8 后再上传（见 3.4 节），这次还没做。
- 限制：只能通过 Wi-Fi 传书页导入；转换在手机或电脑上进行，大书要等几秒。没有 `DecompressionStream` 的浏览器会提示换用 Safari 或 Chrome。
